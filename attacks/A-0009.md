## Attack

A local service holds secrets and wants to let a sanctioned local app use one
without ever handing over the value. The natural design:

```
POST /v1/custody/inject
  gate: _require_loopback(request)
  gate: X-OpenVault-Reveal: intentional
  gate: vault is unsealed
  -> the vault types the secret into the focused field
```

Every gate looks like a check. None of them identify a caller.

1. **Loopback is not a process boundary.** OpenVault's own
   `docs/SECRETS_CUSTODY.md:281-284` says it: any process running as the user
   reaches 127.0.0.1. The check answers "is this machine" and is read as
   "is this the app I trust".
2. **The header is supplied by whoever is calling.** `X-OpenVault-Reveal:
   intentional` is a string the client writes about itself. So is
   `x-openfree-identity: {deviceId}`, which the requesting client also sends.
   A second process copies both from a packet capture, or from the source.
3. **Unsealed is a state, not a permission.** Once the user unseals for their
   own work, it is unsealed for everything on the box.

So the endpoint's authority rests entirely on the request that asks for it.
That is the same shape as `A-0005` - authority travelling on data the asker
controls - moved across a process boundary that was never actually closed. It
is worse here than in A-0005, because the thing granted is a credential rather
than a click.

The attack needs no exploit: any script the user runs, any npm postinstall, any
other agent on the machine, POSTs the same three things and the vault types a
password or a one-time code into whatever has focus.

## What it found

Found by review before the code existed, while ordering a build. The proposed
build order had:

- rank 1: ship `POST /v1/custody/inject`, marked `depends_on: "None. Unblocked today."`
- rank 2: make the app-grant pairing code real - "the prerequisite that makes
  rank 1's approval meaningful"

The plan contradicted itself in adjacent entries and still declared rank 1
unblocked. Shipping in the stated order gives the vault an endpoint that types
secrets on demand for any process running as the user, with a human approval
prompt that cannot say *which* process it is approving.

The fix was already half-built and unused: `vault/app_grants.py:144`
`decide_grant()` renders a pairing code that nothing compares. Comparing it with
`hmac.compare_digest` binds the approval to the process that asked.

Related, same estate, same class of "a gate that does not gate":
`POST /v1/contract/ledger/append` in Cortex has no auth dependency and takes
`actor` verbatim from the body, while the sibling `sidecar_routes.py:74` already
demotes a client-supplied actor to payload detail. And adding RBAC alone would
not have fixed it: `_DEMO_KEYS` are the default when `DMS_API_KEYS` is unset,
the launcher seeds them, and they are printed in the repo - so the gate would
move from "POST anything" to "POST anything with a string from the README".

## Corpus case

Any endpoint that hands out or types a secret must answer, in a test:

> Which process is this, and what proves it?

If the only answers are localhost, a header, and a global unsealed flag, the
answer is "any of them" and the test must fail. The binding fact has to be
something the requester cannot mint: a pairing code compared server-side, a
named pipe or Unix socket with peer credentials, or an OS-level token.

Pin it as a negative test - a second client sending byte-identical headers from
the same machine must be refused - not as a positive test that the sanctioned
client succeeds. A positive test passes for the attacker too.

## Reuse

Apply this lens to any "local trust" boundary:

- `_require_loopback`, `127.0.0.1` allowlists, `--host localhost`
- `X-*-Intentional` / `X-*-Confirm` / `?force=true` style headers and params
- "the vault is unlocked" / "the user is signed in" as a per-call permission
- device ids, install ids, and client names sent by the client

Ask of each gate: does it identify the CALLER, or does it merely describe the
CALL? Only the first is authority. The second is the asker's own claim about
itself, and `A-0005` is what happens when the two are confused.

Order matters as much as the check: a pairing or attestation step that ships
*after* the endpoint it is supposed to bind has shipped nothing at all, because
the unbound version is already in the wild and already trusted.
