## Expected vs actual

Expected: a Ticket Runner handed tickets #15 / #19 / #20 (EPIC-P02, repo `D:\Pointer`)
reads the issues, reads the cited code, and implements. The brief described the code as
unfixed and quoted the vulnerable lines.

Actual: the fix for #15 was ALREADY IN THE TREE, uncommitted, written minutes earlier by a
second Claude Code process working the same three tickets in the same working directory.
Had the second lane started editing, both lanes would have written `electron/main.js`,
`electron/netie/safety.js` and `electron/hud.js` concurrently, each on a stale read.

Every coordination surface the operating protocol tells an agent to check said the work
had not started:

- `gh issue view 15|19|20` - all three bodies still read `current: 0 / 5 - not started`,
  and all three had `comments=0`. The first lane never advanced its Step counter.
- `git status --short` - `electron/netie/safety.js` shows as ` M` whether one lane or two
  is editing it. `git status` reports content state, never authorship or liveness.
- `STATUS.md` - unchanged; it is updated at end of run, not at start.

The only signal was outside git entirely: file mtimes moving while the session read them.
`electron/netie/safe-path.js` 20:52, `word-coworker.js` 20:53, `safety.js` 20:54,
`main.js` 20:58 and again 21:00, against a session that had written nothing.

## Reproduction

1. Dispatch two Ticket Runners at the same repo checkout for the same epic.
2. In the second, before editing, snapshot mtimes:
   `ls -la --time-style=full-iso electron/netie/*.js electron/main.js`
3. Read a file the brief quotes as vulnerable. Observe the fix is already present.
4. Re-list mtimes 60s later - files advance with no write from this session.
5. Confirm liveness, not just recency, from the process table. Windows:
   `Get-CimInstance Win32_Process -Filter "Name='claude.exe'"` and compare
   `CreationDate` against own ancestry (`Win32_Process` walk from `$PID`); then sample
   `(Get-Process -Id <pid>).CPU` a few times. Rising CPU means mid-run, not idle.

Observed here: own session PID 38204 (17:54:44); the other lane PID 35928 (20:47:04),
CPU 74.3 -> 77.9 over 60s while `main.js` kept advancing.

## Root cause class

Liveness is not a property of the repository. The document system routes work through
GitHub Issues (R-0013) and treats the issue as the source of truth for state, but an
issue records intent, not occupancy. Nothing in git or GitHub answers "is another process
holding this file right now", and both lanes had every reason to believe they were alone.

The Step-counter rule is the intended occupancy signal - "update `Step: current: N / M`
BEFORE starting each step, so an interrupted run leaves an accurate position". It fails
open: a lane that skips it is indistinguishable from a lane that has not started, and the
cost of that ambiguity is paid by the second lane, which cannot tell the difference from
the outside. An advisory lock that only the well-behaved take is not a lock.

Same class as R-0006 ("several lanes work these repos at once") one level up: R-0006
protects the index from a careless lane, this protects the working tree from a second
lane that is behaving perfectly and simply does not know.

## Invariant gap

Missing rule. R-0006 covers staging discipline within a lane and R-0003 covers who
verifies, but nothing requires a lane to establish that the tree is unoccupied before it
writes. Candidate, to be proposed as a rule only after a second occurrence:

> Before the first edit of a run, confirm the working tree is unoccupied: no source file
> has an mtime newer than the run's own start with no write from this run. If one does,
> stop and report rather than edit. Advancing the ticket's Step counter before step 1 is
> what makes a lane visible to the next one - a run that skips it is invisible, so treat
> the counter as load-bearing, not as bookkeeping.

## Notes

The second lane stopped without editing and reported BLOCKED. Nothing was lost.

Detection cost was about four tool calls; the alternative was two agents interleaving
edits into `main.js` and `hud.js` with no merge base, since all of it was uncommitted.

Secondary observation, unrelated to the collision and worth its own ticket: in
`D:\Pointer`, `hud:openPath` is absent from the `INVOKE` allowlist in
`electron/hud-preload.js`, while `electron/hud.js:568` invokes it for the status-pill
"Open" button. That call is rejected with `blocked hud:openPath` before it reaches main,
so the button does nothing today. It narrows D5's reachable surface and it is also a
legitimate control that refuses legitimate work (R-0005).
