## Expected vs actual

**Expected (Cortex#14):** a buyer uploads a workbook, asks about it, and either
gets an answer about their file or is told the system cannot answer.

**Actual:** `route_to_metric` matched on the words "total" / "revenue" /
"amount" and compiled a governed metric over `transactions` - the vendor's own
synthetic demo warehouse - returning a confident number about data the customer
had never seen, badged `governed_metric`.

The second half was the surprise. `enforce_manifest` **was already refusing
this**. It refused by raising `PathNotAllowed` from inside execution, and the
ask route mapped that to an HTTP error. So the control worked and the product
still failed: the buyer saw a crash, not a refusal, and nobody reviewing the
enforcer would have found a gap - because there wasn't one.

**Expected (Cortex#6):** the enforcer guards every read.
**Actual:** it guarded `/v1/contract/*` only. `POST /dms/query` - the demo and
product path - executed SQL on a bare connection. Four separate executors, not
one: the answer path's `else:` branch, the total-count helper, the plausibility
prober, and a legacy ranked path reachable through a bridge.

## Reproduction

```python
# Cortex#14 - bind a manifest that does NOT grant the demo warehouse
v = VerifiedManifest(manifest=Manifest(row_predicates={"q3_sales_export": "TRUE"}, ...), ...)
answer("what is the total amount in the Q3 sales export", verified=v)
# -> raises PathNotAllowed; over HTTP, an error response rather than an abstain

# Cortex#6 - the product path never had a manifest at all
query_service.answer_question(q)   # -> _engine_answer(q, session_id=...), no `verified`
```

## Root cause class

**Two classes, and they are the interesting part.**

1. **A control that fails by raising is only half a control.** Fail-closed
   decides *whether* to refuse; it says nothing about whether the refusal is
   legible where the customer stands. Auditing raise-sites finds nothing wrong,
   because the defect is in the mapping from refusal to artifact. The fix is a
   legible gate *in front of* the enforcer, with the enforcer untouched and
   still the boundary that holds - never relaxing the enforcer to "fix" the
   experience.

2. **`Optional[Credential] = None` silently means "unenforced".** A parameter
   whose absence disables a security control puts the control's reach in the
   hands of whichever caller forgot it. Redefining `None` as "mint a narrow
   self-issued grant" removes the unenforced state entirely without forcing a
   manifest onto every call site. The mint must be visibly weaker than the real
   thing (distinct issuer id, empty signature, disclosed on the envelope), or
   it becomes a way to fabricate authority.

Corollary worth keeping: **deleting an ungoverned executor is verifiable.**
After the change the linter reported `guard_and_execute`, `get_connection` and
`read_only_queries_enabled` as unused imports - that unused-import list is the
proof the bypass is gone rather than merely unreachable.

## Invariant gap

- **R-0001** ("gates assert the artifact the customer receives") is the rule
  that should have caught #14, and it nearly does - but it is written about
  *gates*. It did not obviously extend to *refusals*. A refusal is an artifact
  the customer receives too. Proposed sharpening: assert the customer artifact
  on the refusal path, not only the success path.
- **R-0011** ("a silent fallback is a lie") covers the self-issued grant, and
  is why `grant_kind` is on the envelope rather than only in a log line.
- **Missing rule** for class 2: no current invariant says an optional argument
  must never be the difference between enforced and unenforced.

## Notes

Both tickets were one root cause seen from two ends: the router could not state
which tables its plan would read, and nothing intersected that against the
session grant. Fixed once, in a helper that reuses the enforcer's own name
resolution (`_named_tables` minus `_cte_names`), so the advisory check and the
boundary can never disagree about what counts as a table.

R-0007 held up well here: both gates were disabled and observed to fail before
being trusted green (6 of 6, then 4 of 8). R-0005 controls were included in
each - a session that *does* grant the table still answers normally.

Honest residual: 5 lakehouse tests fail in this environment because a live
engine holds DuckDB's exclusive lock. Recorded as failing per R-0002, verified
environmental by stashing the changes and reproducing identically.
