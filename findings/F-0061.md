## Expected vs actual

**Expected:** a finding with `status: verified` describes behaviour on a default branch.

**Actual:** a 2026-08-23 subagent finding (`openvault-cortex-apikey-bind`, status
verified) describes a loopback verify route and a Cortex `verify_issued_key` that live
only on `cursor/ov-apikey-verify-bind`, `feat/apikey-loopback-verify` and
`cursor/constructor-cortex-mount`. Its own "questions left open" said the branches were
never pushed. Nineteen days later a PRD intake cited it as the reuse path for #211
identity work.

## Reproduction

1. `git -C D:\OpenVault merge-base --is-ancestor 7ad180b1b origin/main` -> false.
2. `grep -rn "apikeys/verify" D:\OpenVault\OpenMW` -> no match.
3. `git -C D:\Cortex grep verify_issued_key origin/main` -> no match.

## Root cause class

Verification recorded against a working tree instead of a commit reachable from the
default branch: the finding carries no oid or branch field.

## Invariant gap

R-0008 (uncommitted or unmerged work does not exist) and R-0001. Candidate rule: a
finding's verify line names the oid and branch, and `verified` is only allowed for an oid
reachable from `origin/main`.

## Notes

The stale finding now carries a dated correction. Cortex #211 instead presents an
OpenVault-issued `ov_` key that OpenVault verifies on its own chat route.
