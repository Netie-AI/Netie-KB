## Expected vs actual

**Expected:** DR-0005 part 4 lists the origin of a SQL-sourced bronze table as `source`,
`extracted_at`, `row_count`, `truncated`, `ref_id`. A steward previewing a capped table
sees that it was capped.

**Actual:** `record_source_pull` stored `source` and `extracted_at` as columns and folded
`row_count` and `truncated` into the `sha256` fingerprint - so a re-pull with a different
row count was *detectable* as a different ingest, but nothing could *read* how many rows
landed or whether the pull was capped. `GET /v1/library/bronze/{table}/preview` of a
`max_rows=2` pull over a three-row source returned `row_count=2` with no truncation field.
The epic's own acceptance sentence: *a capped table presented as complete is a wrong number
waiting to happen.*

The implementer (this lane) chose the fold deliberately, to avoid widening a table other
lanes read. The verify-agent, a different run, saw what the implementer could not: the
choice traded a readable field for a hash input, and DR-0005 asked for fields.

## Reproduction

```
pull = ingest_source_table(cfg, "orders", max_rows=2, path=wh)   # 3-row source
assert pull.truncated is True                                     # receipt: fine
GET /v1/library/bronze/dbo_orders/preview                         # customer artifact
  -> row_count: 2, no truncated key                               # says "two-row table"
SELECT * FROM bronze._ingest_registry                             # columns:
  table_name, filename, sha256, ingest_id, created_at, space_id   # no row_count, no truncated
```

## Root cause class

**Provenance folded into a fingerprint.** A hash proves that two states differ; it cannot
say how. Any field a person needs to *read* - a count, a flag, a timestamp - must be stored
as itself. Folding it into a digest to avoid a schema change keeps the information
technically present and practically gone, which is R-0011's silent-degradation shape
applied to metadata rather than to a result.

Second-order cause: the R-0001 test was scoped to two of DR-0005's four fields (`source`,
`extracted_at`) and passed, so the artifact assertion existed and was incomplete. An
artifact test that covers half the contract certifies half a feature as whole.

## Invariant gap

R-0001 held in form and not in substance. The gap is a habit, not a rule: **when a decision
record enumerates fields, the R-0001 test enumerates the same fields.** Four in the record,
four on the artifact. The verify-agent charter already says "verify the assertion, not the
implementation"; this adds "and count the fields in the assertion."

## Notes

Fixed on the same PR by the widen-if-missing idiom `_ensure_registry` already used for
`space_id`, a named-column insert so the next widening cannot misalign a positional one,
and `truncated` plus a note on the preview response - asserted on the HTTP body, and with
an R-0005 sibling asserting an uncapped pull does not cry wolf.

The verify-agent reproduced the R-0007 probe with its own hands before reporting, and
found the collision in A-0008 in the same pass. Seven hundred seconds, two real defects,
neither visible to the run that wrote the code. That is the whole argument for R-0003.
