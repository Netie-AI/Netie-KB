## Expected vs actual

**Expected:** SQLSRC-06: MySQL InnoDB accepts `FOREIGN KEY (cust_ref) REFERENCES customers(cust_ref)` when `customers` is keyed on `(cust_ref, version)` and `cust_ref` is only a non-unique index. That is the live lying-FK shape. `verify()` / `compile()` then refuse the link and show inflated 90 vs true 60.

**Actual:** `docker.io/library/mysql:8` resolved to **8.4.11**. CREATE TABLE failed:

`ERROR 6125 (HY000): Failed to add the foreign key constraint. Missing unique key for constraint 'FK_Orders_Customers' in the referenced table 'customers'`

So the ticket's "InnoDB accepts this" is false on current `mysql:8`. The same class as SQL Server: the lying FK is unbuildable. Collect still ran after dropping the constraint: `skipped: ["secrets"]`, items truncated 1000, PK `(cust_ref, version)` read correctly, `declared_foreign_keys: 0`. Landed rows still fan out if you JOIN (60 vs 90), but `from_manifest` has no link, so `compile()` refuses `no_path` rather than `fanout_refused` naming the link.

## Reproduction

```
docker run mysql:8
SELECT VERSION();  -- 8.4.11
CREATE TABLE customers (cust_ref, version, PRIMARY KEY (cust_ref, version), KEY (cust_ref));
CREATE TABLE orders (..., FOREIGN KEY (cust_ref) REFERENCES customers(cust_ref));
-- ERROR 6125
```

## Root cause class

**Engine version drift the fake DB-API cannot see.** The unit fixture injects an FK row. A real 8.4 catalog will not. The ticket text described 8.0-era InnoDB.

## Invariant gap

SQLSRC-06 MySQL ontology block cannot pass on `mysql:8` today. Re-run needs `mysql:8.0` (or any InnoDB that still allows a non-unique referenced index), or the ticket must treat 8.4 the same as SQL Server: live-only class is something else (here, the join of landed rows still inflates, but there is no declared link to refuse).
