## Expected vs actual

**Expected:** SQLSRC-06 runs a real MySQL 8 with the lying FK
(`FOREIGN KEY (cust_ref) REFERENCES customers(cust_ref)` against a non-unique
index), then the ontology refuses the fan-out (unit fixture sums 60 vs 90).

**Actual:** `mcr.microsoft.com/mssql/server:2022-latest` was already local and ran.
`mysql:8` was not. `docker pull mysql:8` sat for >25 minutes with three layers still
"Pulling fs layer" after others "Already exists". Retry against
`public.ecr.aws/docker/library/mysql:8` failed `TLS handshake timeout`. Official
Windows zip HEAD returned 403. No host mysqld. WSL bash missing. Path (B)
customer staging did not run. MySQL line on SQLSRC-06 is FAILED, not a skip
(R-0002).

## Reproduction

```
docker pull mysql:8
# observed: partial layer cache, remaining layers never left "Pulling fs layer"
# Head https://registry-1.docker.io/v2/library/mysql/manifests/8 -> TLS handshake timeout
```

## Root cause class

**Registry reachability, not the connector.** The fake DB-API also hid MySQL 8
`caching_sha2_password` / `PyMySQL[rsa]` and `TABLE_SCHEMA = database` filters;
those did not get a chance to fire because the engine never started.

## Invariant gap

R-0002: a dialect that did not run is a failed line. EPIC-020 must not report
COMPLETE. Re-run when `mysql:8` pulls, seed `sales` as the ticket describes, do
not weaken tests.

## Notes

SQL Server path A DID run (F-0046, F-0047). Do not substitute MariaDB or a fake
and call it MySQL. Host pyodbc + PyMySQL were already installed; the missing piece
was the MySQL server process.
