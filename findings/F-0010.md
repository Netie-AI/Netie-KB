## Expected vs actual

Expected: a request to "harvest skills from desktop snapshots" would be new
capture surface, and would be routed as such before any capture code existed.

Actual: a screen capture loop already ships and runs by default. Routing the
request found it rather than proposing it. Three separate gaps, and only the
first is the one anybody was looking for.

1. `recall: true` and `recallLite: true` are DEFAULTS (`electron/netie/features.js:10-12`).
   `startRecallDaemon` (`electron/main.js:1306-1322`) runs `setInterval` at
   15000ms, or 5000ms when `recallLite` is off, calling `desktopCapturer.getSources`.
   `NETIE_LIGHT=1` does not disable it - `LIGHT_DISABLED` is
   `[systemAudio, canvas, hotTicks]` only (`features.js:15`).

2. Every frame evicted from the 60s ring is sealed to
   `<dataDir>/recall/<id>.enc.json` (`electron/netie/clicky/recall.js:60-85`)
   carrying `fgTitle` and `fgProc` - the foreground window title and process
   name. Pixels are included only under `NETIE_RECALL_PIXELS=1` or
   `NETIE_HQ_CAPTURE=1`. Grep for ttl/purge/retention/expire/prune/maxAge over
   `recall.js` and `main.js` returns nothing: the directory grows without bound.

3. `capture-gate.shouldAcceptFrame` has exactly one production call site,
   `main.js:2911`, and its state is `{ source, listenMic, listenSystem, paused }`.
   It is an audio gate. The screen path has no equivalent gate, no arm step, and
   no HUD control.

## Reproduction

```bash
cd D:\Pointer
grep -n "recall:\|recallLite:\|LIGHT_DISABLED" electron/netie/features.js
grep -n "function startRecallDaemon" -A 16 electron/main.js
sed -n '60,85p' electron/netie/clicky/recall.js
grep -rniE "ttl|purge|retention|expire|prune|maxAge" electron/netie/clicky/recall.js
grep -rn "shouldAcceptFrame" electron/          # one production call site
```

Runtime: launch the app, leave `state` out of IDLE, wait past the 60s ring
window, then list `<dataDir>/recall/`. Files accumulate and nothing removes them.

## Root cause class

Two classes, and conflating them is why this survived.

**Class 1 - an invariant written for one modality is read as covering the
surface.** `docs/SAFETY.md` invariant 8 ("Arm to listen") is genuinely scoped to
audio: it says "before it is transcribed" and "Transcription is on-device".
It is not violated. The defect is that no invariant covers the screen path at
all, so a reader auditing capture finds a gate, finds tests for that gate
(`test/acceptance/privacy-hud.test.js`), and concludes capture is gated. An
absent invariant reads as a satisfied one when a sibling invariant is present
and well tested. Naming a modality in an invariant title obliges naming every
other modality that reaches the same class of sink.

**Class 2 - retention is treated as a property of encryption.** The frames are
sealed with two KEKs, so the at-rest exposure was reasoned about and solved.
Unbounded lifetime was not, because "it is encrypted" answers a different
question than "how long does it exist". Sealing is not a retention policy.

## Invariant gap

`R-0011` (a silent fallback is a lie) is the closest active rule and does not
reach this. R-0011 governs degradation - a smaller model, a cached key, demo
mode - and this is not degradation. It is a capability running as designed and
undisclosed.

**Missing rule, proposed:** standing background collection is disclosed in the
product surface, is switchable by the user from the product surface, and carries
an explicit retention bound. Encryption at rest does not satisfy any of the
three. A capability the user cannot see and cannot stop is not gated by the fact
that it is encrypted.

Note the interaction with `A-0007`: that attack closed the skills act path
against Cortex `/dms/secure`. This finding is the same trust question one layer
earlier - what may be collected - rather than what may be executed. A harvest
feature built on this corpus inherits both.

## Notes

Scope qualifier that matters, and that the routing pass initially overstated:
the daemon is not literally always on. `shouldRunRecall` (`main.js:1329-1331`)
returns `state !== "IDLE" || clickyState === ClickyStates.CLICKY`, so it runs
whenever the app is out of IDLE, not from launch. That narrows exposure. It does
not change disclosure, control, or retention.

**Not the first pass over this, and the earlier one measured what this one only
reasoned about.** Pointer commit `e611cc2` (2026-08-19) independently verified the
same capture loop under R-0003 and recorded numbers this finding does not have:
4177 sealed records, 20 MB on that machine, a foreground window-title and process
timeline at 5-15s cadence, absent from the ten toggles in the HUD settings menu.
It also sharpened one point worth carrying: the 60s ring bounds MEMORY only,
because both eviction bounds call `_sealEviction`, which writes the evicted frame
to disk - ageing out of the ring is filing, not deletion. Its one-line conclusion
is the right one: encryption is not the gap; disclosure, retention and a control
are.

What this finding adds beyond that commit is only the invariant analysis: that
`capture-gate.shouldAcceptFrame` is audio-only with a single production call site,
that no screen-path equivalent exists, and the two root-cause classes above. The
capture facts themselves were already established and committed. Recorded this way
so the next reader does not treat this as a second, independent sighting - it is
one sighting plus a later analysis.

Found while routing a founder feature request ("harvest skills from desktop
snapshots, constantly web search, central skill library") through `prd-agent`.
Routed as proposed EPIC-P08 plus `DR-0003`, both pending a founder call. The
general lesson is the one worth keeping: routing a request for a capability is a
cheap way to discover you already shipped it. The PRD question "should we build
this" forced an inventory that "how do we build this" would have skipped.
