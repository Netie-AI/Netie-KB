## Expected vs actual

Expected: a test asserting `appendDocx({ path: <outside the sanctioned root> })`
returns `ok: false` proves `appendDocx` enforces containment.

Actual: it proved nothing about `appendDocx`. Deleting `appendDocx`'s containment
check entirely left the test green.

The function begins:

```js
const contained = containPath(outPath, [sanctionedRoot()]);
if (!contained.ok) return { ok: false, reason: contained.reason, ... };

// Appending to something that is not there yet is a create.
if (!fs.existsSync(outPath)) return writeDocx({ text, path: outPath, ... });
```

The test used a path that did not exist. With the guard removed, control fell to
the delegation branch, `writeDocx` applied **its own** containment check, and the
refusal the test asserted still arrived - from a different function, for a
different reason. The assertion was satisfied by the fallback, not the feature.

The dangerous case is the exact inverse of what was tested. Appending to a file
that **already exists** outside the root never reaches `writeDocx`, so that path
had no coverage at all - and it is the one that modifies a document the customer
already has.

## Reproduction

```bash
cd D:\Pointer
git show 1488c2f -- electron/netie/word-coworker.js | grep -n "existsSync" -B 6
```

Mutation, which is how it was found: neuter `appendDocx`'s own containment while
leaving `writeDocx`'s intact, then run `node test/word-coworker.test.js`. Before
the fix that exits 0; after it, 1.

The fix is a test that seeds a real package outside the root first (temporarily
moving `NETIE_WORD_OUT_DIR`, which `sanctionedRoot()` reads at call time by
design), then asserts both the refusal and that the file's sha256 is unchanged.

## Root cause class

**A guard test is only valid if the code under test is the only thing that can
produce the asserted outcome.** When a function guards, then delegates to another
function that guards the same way, any input reaching the delegation branch is
unusable as evidence about the first guard. The test and the guard were both
correct in isolation; the test simply could not distinguish them.

This generalises past containment. Any layered defence has the shape - an outer
check plus an inner one - and layering is usually a virtue. What it costs is that
the outer layer becomes untestable through inputs the inner layer also catches.
The input has to be chosen so only the outer layer can refuse it, which for a
delegating branch means an input that never reaches the delegate.

Note the interaction with `R-0004`: fixing at the class means the same guard often
ends up in several functions, which is right, and which is exactly what creates
this blind spot. The two rules pull in the same direction, and the test has to be
written to tell the layers apart.

## Invariant gap

`R-0007` caught this, so this finding is evidence for keeping that rule rather
than a gap in it. Two of the six gates written in that pass were blind on their
first mutation run - in code written minutes earlier, by a run that believed the
tests were good, with the whole suite green. Without a mutation pass both would
have shipped as "tested".

What `R-0007` does not currently say, and should when it is next revised: mutate
**the specific line**, not the feature. The first mutation attempt on `#21` in the
same session disabled a transcribe-time consent guard, saw the suite stay green,
and nearly recorded "the cloud-consent gate is untested". The real gate was one
call earlier in `probe()`; mutating that turned two tests red. A surviving mutation
means one of two things - the gate is untested, or the mutated line is not the gate
- and the second has to be ruled out before reporting the first.

## Notes

Found while implementing Pointer ticket `#17` (`appendDocx`), committed as
`1488c2f`. Sixteen mutations were run across `#12`-`#25` and the new `#17` gates;
fourteen were caught immediately, and the two that were not were both in code
written in that same pass - not in the older code being verified. The pass that
writes a gate is the pass least able to see that it is blind, which is the same
argument `R-0003` makes about fixes and is worth stating about tests too.

A second, smaller find from the same fixtures: the pre-existing `docxText` test
helper matched `<w:t[^>]*>`, which also matches `<w:type w:val="nextPage"/>` - an
element real Word documents carry inside their section properties - so it returned
markup as if it were the customer's prose. A test helper that parses with an
approximation is a false-green generator in the same family as `F-0005`.
