## Expected vs actual

**Expected:** after an operator sets a vault passphrase, the vault directory is unusable
to anyone who copies it without the passphrase. `apps/web` on `:3010` says "passphrase
configured", and the OpenVault PRD asserts it directly: "WHEN I copy the vault folder to
another account/machine without unwrap rights, THE SYSTEM SHALL make the ciphertext
unusable."

**Actual:** the v0 migration path deliberately leaves the raw pre-wrap key next to the
wrapped one, forever. `_migrate_plaintext_key`
(`OpenMW/openmw/openvault/vault/crypto.py:61-82`) writes `master.key.v0.bak` - 44 bytes,
a raw Fernet key - and its docstring states the backup "stays until the user removes it".
Both local vaults on this machine carry one, with an mtime matching `master.key` exactly.

The bypass is total. `keywrap.is_wrapped` (`vault/keywrap.py:263`) is nothing more than a
check for the four-byte `OVK1` magic, so a raw key fails it, `Seal.__init__` takes the
not-wrapped branch, and `_load_or_create_master_key` uses `blob.strip()` as the Fernet key
directly. Renaming the backup over `master.key` in a copied folder opens every sealed row
in `keys.db` on any machine, under any account, with no passphrase and no DPAPI.

`Seal.set_passphrase` (`crypto.py:238-251`) rewraps under scrypt and logs
`vault_passphrase_configured` without ever looking for the file sitting beside the key it
just wrapped.

## Reproduction

No code change needed; the artifact is already on disk. Read-only version, safe to run:

    python -c "
    from pathlib import Path
    d = Path.home()/'.openvault'
    print('wrapped :', (d/'master.key').stat().st_size, 'bytes',
          (d/'master.key').read_bytes()[:4])
    b = d/'master.key.v0.bak'
    print('backup  :', b.stat().st_size, 'bytes', b.read_bytes()[:4])
    "

    wrapped : 368 bytes b'OVK1'
    backup  : 44 bytes b'gAAA'   <- no magic, so is_wrapped() is False

The destructive half - copy the folder elsewhere, rename `master.key.v0.bak` to
`master.key`, open `keys.db` - was **not** executed. It follows from reading
`crypto.py:100-114` and `keywrap.py:263`, and it must be proven by a different run
against a throwaway vault (R-0003). Do not test it by moving the real backup.

## Root cause class

**A migration wrote a recovery artifact whose threat model is the inverse of the thing it
was migrating toward, and nothing was required to reconcile the two.**

Not "someone forgot to delete a temp file". The backup is correct in isolation - losing a
master key is worse than leaking one, and the docstring argues that honestly. It is wrong
in composition, because the whole purpose of the migration was to make the key
non-portable, and the backup restores portability permanently.

The generalisation, which is what makes this worth a rule: **any recovery copy taken
before a hardening step defeats that hardening step for as long as it exists.** Wrapping
the backup does not help - the backup exists precisely for the case where the wrap cannot
be unwrapped, so a wrapped backup is a second copy of the same failure. The only shapes
that survive are "delete after verification" or "keep, but make its presence visible in
the artifact the customer receives".

## Invariant gap

**R-0011 should have caught this and did not, because R-0011 is currently read as a rule
about fallbacks.** "A silent fallback is a lie - any degradation must be visible in the
output, not just in a log line." Here there is no fallback and no degradation event. The
protection was never delivered at all, and there is no moment where a code path chose a
weaker option and could have announced it.

R-0011 wants a second sentence: **a protection that is claimed must be reported from the
artifact that would falsify it.** `Seal.status()` derives `passphrase_configured` from an
in-process wrap method; it should derive from the directory, because the directory is what
the operator copies.

**R-0001 explains why the tests passed.** `OpenMW/tests/test_keywrap.py:142` asserts
`assert (tmp_path / "master.key.v0.bak").is_file(), "migration must leave a backup"`, and
`:180` asserts the unwrap-failure message names it. The suite asserts on the key file, an
intermediate artifact. The artifact the custody customer receives is the **vault
directory**, and no test asserts that a copied directory fails to decrypt. This is R-0001
in a shape it has not been recorded in before: the intermediate artifact was not a
generated string or a SQL statement, it was one file inside the folder that is the real
deliverable.

**Do not read this as an argument to delete the backup by default** - that would be R-0005
(a control that refuses legitimate work is a failure). The recovery need is real.

## Notes

Two facts about the shape of this defect that generalise past OpenVault:

**A defect can be a tested contract.** Two tests assert the leak. An agent asked to "fix
the plaintext key" would break them and either weaken the tests to go green - forbidden -
or conclude the behaviour is intended and stop. The routing rule that survives: when the
defect is asserted by a passing test and argued for in a docstring, it is a decision
record, not a patch.

**Check whether the defect has shipped before pricing the fix.** Here it had not.
`main` and `origin/main` still carry the pre-keywrap 52-line `crypto.py` with zero
references to `_migrate_plaintext_key`; the 260-line version exists only on three unmerged
branches where it is byte-identical (md5 `83bcfb888d51`). Fixing before merge is a branch
edit; fixing after merge is a migration against live operator vaults. The corollary is a
new hazard class worth naming - **an identical file on N unmerged branches means the last
merge wins, so a security fix landing on one branch is silently reverted by the other
two.**

That hazard has a general resolution, and it is the reusable half: **land the fix and its
guard in the same commit, so the first merge arms the guard on `main` and every later
merge that reverts the fix fails loudly.** Ordering the merges does not help - it only
selects which merge is dangerous. A control that fails on the reverted tree removes the
ordering question entirely.
