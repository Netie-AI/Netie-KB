## Expected vs actual

Asked the live stack: `total revenue for SKU-00397`.

- Expected: the per-SKU revenue, or an abstain - the pack has no per-SKU revenue
  metric, so abstain is the only honest answer.
- Actual: `sku_count = 509` - the count of every SKU in the warehouse - with
  badge `L1_GOVERNED_METRIC`, `abstained: false`, and a drillthrough token.

Wrong for every SKU, real or invented, so no per-SKU question was safe. The
badge and token are what make it confidently wrong rather than a miss.

## Reproduction

```bash
curl -s -X POST http://127.0.0.1:8090/v1/chat/ask \
  -H "content-type: application/json" \
  -d '{"question":"total revenue for SKU-00397"}'
# text: "Result: sku_count = 509"   badge: L1_GOVERNED_METRIC
```

Offline: `route_to_metric("total revenue for SKU-00397")` -> `MetricPlan("sku_count")`.

## Root cause class

A router branch matched on the *word* `sku` via `\bskus?\b`, which also matches
*inside the identifier* `SKU-00397` because the hyphen is a word boundary. So a
question about one entity satisfied a population-level aggregate branch.

The class is not "that branch's regex". It is: **when a token appears both as a
domain word and inside an entity identifier, every sibling branch keyed on that
token carries the same defect, and they fail in different directions.**

Demonstrated: excluding the `sku_count` branch did not fix the bug - the same
wrong answer moved to `revenue_total = 80,375,993.99`, the whole warehouse's
revenue reported as one SKU's, because *that* branch's guard tests the
**normalized** text, where the identifier no longer reads as "sku". Two branches,
two different text views, one defect. Patching branch-by-branch would not have
converged; there are ~30 branches in the cascade.

Fix at the funnel, not the branch: one post-check on the way out of the router -
if the question names a concrete entity, the returned plan's slots must contain
it, else return None. Exclusion asks pass untouched, because they resolve the
entity into `exclude_skus` and it is therefore in the slots. That property
("the plan is about the thing you named") is checkable once and holds for every
branch, present and future.

## Invariant gap

R-0004 (fix the root cause class) is the rule that applies, and the first attempt
violated it by special-casing the one branch that surfaced the bug - the exact
shape R-0004 names. Worth adding as a **detection heuristic** rather than a new
rule:

> When a router keys on a bare domain word, grep the corpus for that word
> appearing inside an identifier. If it does, the guard belongs at the funnel.

R-0001 is what found it: the defect is invisible in generated SQL review (the SQL
for `sku_count` is perfectly valid) and only appears when you read the rendered
answer against the question asked. The offline corpus was 376/376 wrong=0
throughout - it simply contained no `<metric> for <specific-entity>` phrasing,
which is also why claim_n=47 must not be reported as "0 wrong".

R-0005 gated the fix: population asks (`how many SKUs`, `count of unique SKUs`,
`total revenue`) and the exclusion confirm path all had to keep working, and the
full corpus had to stay wrong=0 with no new abstains. Verified by neutralizing
the new guard in-process and confirming byte-identical corpus output.
