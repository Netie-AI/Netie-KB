## Expected vs actual

**Expected:** WRONG=0 on the curated 26 means the served values match the oracles.

**Actual:** `scripts/score_curated.py` `judge()` reads only the expect class, the badge,
`abstained` and row count vs `min_rows`; `load_oracles` runs only in `self_check`, to
confirm each oracle SQL string is non-empty. A planted row (`sku_count=999` where gold is
7) scores LAYER. The offline generative lane is `compute=bind_plan`, a regex/token slot
binder: an audit-hook guard recorded zero socket events, so no Cortex, OpenVault or model
call happens at all. Executing all 15 generative answers against the oracle SQL on the
same lake: 1 exact match, 9 matching modulo alias or one extra column, 2 unverifiable
(the oracle filters `txn_type='OUT'` while the lake stores `outbound`), 2 dropping the
identifier column, 1 wrong (an extra SKU and a COUNT of lots instead of quantity).

## Reproduction

1. `git -C D:\DMS archive d2f116a6` into a scratch dir; run `score_curated.main(['--ab'])`
   with a socket guard -> exact 10/26, gen 15/26, WRONG 0, zero socket events.
2. `judge({'expect':'l0','min_rows':1}, {'badge':'L2_VALIDATED','rows':[{'sku_count':999}]})`
   -> LAYER.
3. Execute each generative-answered oracle on the same lake file and compare columns and
   values.

## Root cause class

A verdict on an intermediate signal (badge plus row count) standing in for value gold.
Same class as F-0017, a gate that never executes what it certifies.

## Invariant gap

R-0001. Also R-0010: at n=26 even a value-correct judge bounds the error rate near 11
percent, so no sub-1-percent claim follows.
