## Expected vs actual

**Expected:** 29 passing tests over the ontology compiler mean a compiled query runs.

**Actual:** every ontology derived from a real database emitted SQL DuckDB could not
parse. The join alias was built as "d_" plus the object name, so a schema-qualified
table produced `LEFT JOIN ... d_Sales.Customers ON ...` - a parse error. All 29
tests asserted `isinstance(got, CompiledQuery)` and stopped. None executed the SQL.
An adversary who RAN a compiled query found it in minutes; two rounds of review by
the author did not.

## Reproduction

Before commit a04db60 in netie/dms:

```
from ontology import from_manifest
o = from_manifest(entry)   # entry with schema-qualified tables, e.g. Sales.Orders
o.verify(con); q = o.compile("revenue", group_by=[("Sales.Customers","region")])
con.execute(q.sql)         # ParserException: syntax error at or near "."
```

## Root cause class

Asserting on an intermediate artifact (the returned object) instead of the
artifact the consumer receives (executed rows). Same class as a gate that asserts
generated SQL and not the rendered answer. The author had written R-0001 into the
same repo that week.

## Invariant gap

R-0001 should have caught it and would have, had the test executed the query.
The gap is procedural: nothing forces a test of a SQL generator to execute the SQL.
Proposed check: any test that constructs a CompiledQuery must call
`con.execute(q.sql)` at least once, or it is not a test of the compiler.

## Notes

Fixed by positional aliases keyed on (object, link), and a test that executes a
derived query and asserts the grouped total conserves. The lesson generalises to
every "compile" step: parse it, run it, compare it - in that order.
