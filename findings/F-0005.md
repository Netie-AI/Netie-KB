## Expected vs actual

**Expected:** an acceptance suite handed over as a TDD harness ("RED until the work packages
land") reports RED until the work packages land.

**Actual:** `npm run test:acceptance` printed `8 passed, 0 failed` and exited 0 against a tree
where six of the eight work packages did not exist. The output contained the truth  - 

```
SKIP [WP-P1-SKILLS-EXEC] missing electron/netie/skills-exec.js
PASS P1-SKILLS-EXEC: skills must be able to expand into actions
```

 -  a SKIP line immediately followed by PASS for the same test. The summary counts only the PASS.

## Reproduction

`D:\Pointer\test\acceptance\run.js`, before this session:

```js
const STRICT = process.env.NETIE_ACCEPTANCE_STRICT === "1";   // default: false

function requireFeature(wp, rel, exportName) {
  const mod = loadOptional(rel);
  if (!mod || ...) {
    if (STRICT) throw new Error(msg);
    console.log("SKIP " + msg);
    return null;                 // <- test body then early-returns
  }
  return mod;
}

T("P1-SKILLS-EXEC: ...", async () => {
  const mod = requireFeature("WP-P1-SKILLS-EXEC", "electron/netie/skills-exec.js", "expandSkillsToActions");
  if (!mod) return;              // <- returns without throwing => counted as PASS
  ...
});
```

1. `npm run test:acceptance` with none of the WP modules present -> `8 passed, 0 failed`, exit 0.
2. `npm run test:acceptance:strict` -> `2 passed, 6 failed`, exit 1.

The strict lane was correct the whole time. The default lane was the one in
`test:agentic-pack`, and `test:agentic-pack` is what gets run.

## Root cause class

**A missing precondition resolved as a pass instead of as a distinct third state.**

Not "someone forgot a flag". The harness has three outcomes  -  passed, failed, could-not-run  - 
and a runner with only two counters has to fold the third into one of them. Folding it into
"passed" makes absence of the feature indistinguishable from presence of a working feature, in
both the summary line and the exit code, which are the two things anything downstream reads.

Same class, different clothes: `pytest.skip` in CI without `-W error::pytest.PytestUnraisable`,
`if not shutil.which("psql"): return` at the top of an integration test, a matrix job whose
`if:` condition is never true, and `python -m importlinter.cli lint` exiting 0 having run no
contracts (R-0007). In every one the gate is structurally incapable of reporting the failure it
was built to report.

The tell is cheap to look for: **a conditional `return` before the first assertion.**

## Invariant gap

R-0002 ("a skipped test is a failing test") states the rule and this is a clean instance of it.
The gap is that R-0002 is stated as a *habit* and nothing enforces it, so it only fires when
someone reads the output carefully  -  and here the output scrolled a SKIP line past directly
above a PASS line for the same test name.

Two enforcements that would have caught it, neither of which requires reading anything:

1. **Default the harness to strict; make lenient opt-in.** `NETIE_ACCEPTANCE_STRICT` defaulting
   to `false` means the safe configuration is the one nobody runs. Invert it: strict by default,
   `NETIE_ACCEPTANCE_SOFT=1` to develop against a partial tree.
2. **Count skips and make a non-zero skip count non-zero exit.** `8 passed, 0 failed, 6 skipped`
   with exit 1 is honest; `8 passed, 0 failed` is not. If the summary cannot say "skipped", the
   runner cannot express could-not-run at all.

Also worth adopting from the fix: each WP acceptance file ends with a **wiring test** asserting
the module is actually loaded and called by the app (`hud.html` loads `netie/hud-live.js`,
`main.js` calls `expandSkillsToActions`). A perfectly-tested module that nothing imports is a
feature that does not exist, and every behavioural test above it stays green  -  R-0001 at the
module boundary rather than the customer boundary.

## Notes

Cheap detector for any repo, run before trusting an acceptance lane green:

```bash
grep -rn "if (!mod) return\|if (missing.length) return\|console.log(\"SKIP" test/
```

Related-but-distinct trap seen in the same file: a test that reports on the *runner's* config
rather than the code (`assert.ok(exists("docs/..."))`). Those pass forever and cost a line of
summary each, which is how `8 passed` looked plausible.

Verified by: `npm run test:acceptance` (green, features absent) vs
`npm run test:acceptance:strict` (red, same tree), Pointer @ 2026-07-31.
