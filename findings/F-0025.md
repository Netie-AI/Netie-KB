## Expected vs actual

**Expected:** two agent lanes drawing from one GitHub issue queue would naturally
partition, because each picks up whatever is still open.

**Actual:** they collide, because "still open" is true for both of them at the moment
each starts. In one DMS session on 2026-08-25 this happened three times:

| ticket | outcome |
|---|---|
| dms#73 | both lanes wrote a boundary invariant. The two assertions were **different** and both worth keeping - one caught a scope check nested behind `if space_id:`, the other caught a route reaching customer data with no `compliance_gate`. Merged by hand. |
| dms#74 | both lanes gated the ungated GETs. One did 3 routes, the other 10. Rebase conflict on the 3 shared files. |
| dms#75 | **fully duplicated.** Both lanes implemented a three-or-four-state `serving_sync` on the ingest receipt, both with an envelope abstention test. The second PR (dms#84) was closed as superseded with nothing worth cherry-picking. |

The wasted work is only half the cost. The other half is that the second lane's rebase
had to resolve a **security-relevant** file it did not write, under time pressure, with
`--ours`/`--theirs` semantics that are easy to invert.

## Reproduction

1. Open a repo with N ready tickets and no claim mechanism.
2. Start two agent lanes, each told "solve the open tickets".
3. Both run `gh issue list`, both see the same top item, both start.

Deterministic whenever the lanes start within one ticket's work-duration of each other.

## Root cause class

**A queue with no claim step is not a work-assignment mechanism, it is a suggestion.**
The class is missing mutual exclusion on a shared resource - the same shape as a lock-free
critical section, and `git` does not provide it because the collision happens before any
branch exists. R-0006 already says several lanes work these repos at once and mandates
`git log` before amend and explicit staging; it addresses the *file* collision and not the
*task* collision that precedes it.

## Invariant gap

**Missing rule.** R-0006 covers the git-level hazard. Nothing covers ticket selection.

Candidate rule: *before working a ticket, claim it with a comment naming the lane; before
starting, re-read the ticket's comments and stand down if another lane claimed it.* A
comment is the right primitive because it is atomic enough at human timescales, survives
in the ticket's own history, and needs no new infrastructure.

Weaker but cheaper alternative: partition by area up front (lane A owns `apps/api`, lane B
owns `packages/executor`), which removes the need to claim at all but wastes capacity when
the queue is lopsided.

## Fourth occurrence - the complementary kind (2026-09-03, EPIC-020)

The first three collisions produced overlapping or duplicate work. The fourth did not,
and the difference is worth naming because it is what the claim step should aim for.

A Claude Code lane committed the SOURCE of EPIC-020 tickets 1-3 (the connector's key
reader, the ontology hook, the registry row) to a worktree branch and pushed. A Cursor
lane (grok-4.6) found that worktree, built ON the committed source, and wrote what the
source lacked: the tests, the preview surface, and a better form of the invariant. It
left them uncommitted and wrote a finding naming the rule "one writer, one worktree,
commit on that branch". The Claude lane then committed that work with the author
named, added the one test the Cursor lane had not (the R-0005 sibling), and ran the
R-0007 probe.

Two lanes, one branch, zero wasted lines. What made it work was not a claim comment -
neither lane posted one - it was that the FIRST lane pushed source early (R-0008) so
the second lane had something real to build on rather than something to re-derive.

So the rule sharpens: claim by comment, AND push the first coherent slice within the
hour. A claim on an empty branch still invites parallel derivation; a claim on a pushed
slice invites completion.

One cost, recorded: the second lane's files appeared in the first lane's worktree
without notice, and the first lane spent three turns trying to patch files whose
content had changed underneath it. Reading `git status` before every write, not just
at session start, would have saved those turns.

## Notes

Three things worth keeping from how this actually resolved:

- **Check before closing.** The duplicate was only identified as duplicate by reading the
  other lane's merged tests and confirming they covered every assertion, including the one
  hardest to get right (the envelope abstention, CLAUDE.md 10a). Assuming duplication and
  closing unread would have lost work; assuming novelty and merging would have doubled it.
- **Not every collision is waste.** On dms#73 both assertions survived into main because
  they caught different things. The merge was worth more than either PR.
- **The other lane's model was better in one place.** It split `ok` into `ok` and
  `not_needed` - a single-warehouse deployment where sync is inapplicable is not the same
  event as a copy that ran and succeeded. Losing to a better design is a good outcome; the
  cost was only that two people paid for it.
