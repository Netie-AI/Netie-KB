## Expected vs actual

**Expected:** the `model` field in `POST /v1/chat/completions` selects what serves, so a
scoreboard keyed by the requested model measures that model.

**Actual:** OpenVault walks its own hop order and `resolve_model` honours a requested id
only when that hop's provider carries it; otherwise the hop serves its own first
catalogued model (`vault/providers.py` resolve_model rules 1-3; `vault/proxy.py`
chat_completions). Cortex PR #214 filed measurements under the requested family label,
and under `openvault` for `auto`, which no candidate reads. With several families armed
the pick stayed `auto` forever; a request for one family served by another hop was still
scored as that family.

## Reproduction

1. `GET http://127.0.0.1:5000/api/freeroute/status` - hops are listed in OpenVault order
   (groq priority 10 first on 2026-09-14).
2. Offline, with the crew chat client monkeypatched: arm three families, call
   `crew.freeroute.complete` five times.
3. `measurements() == {'openvault': {calls: 5}}` and `pick_route` still returns `auto`.

## Root cause class

Outcome attributed to the request instead of the response: the measured subject is read
from intent, not from what answered.

## Invariant gap

R-0011 (the stamp must say what actually served) and R-0001 (measure the artifact
received). The fix records requested AND served, scores the served subject on downstream
validator verdicts, and never scores HTTP refusals (429/503 say nothing about a model).
A first attempt at the fix still hid the rule behind a fallback that made the
served-model line dead code; only a mutation run surfaced that.
