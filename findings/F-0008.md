## Expected vs actual

**Expected:** the racing router learns which architecture wins per task family,
OSR bands a familiar task `known`, and a consumer (Pointer) reuses the proven
plan instead of re-racing.

**Actual:** `arch_families: 0`, `arch_runs: 0`. The scoreboard was empty, so
`best_preset()` returned None for every family, so `BAND_KNOWN` was
**structurally unreachable**. Classifying identical text twice returned `open`
both times. The `known` path had never fired since OSR shipped.

Downstream, this is what stopped Pointer landing: it consumes OSR bands, so it
was told every action was novel, forever.

## Reproduction

```python
from CortexOS.execution import scoreboard, osr
scoreboard.best_preset("anything")        # -> None
osr.classify("summarize my open PRs")     # -> band=open, winner=None
osr.classify("summarize my open PRs")     # -> band=open  (again)
```

Why the board was empty, from `data/engine/action_events.db`:

```
routine_langgraph  langgraph  failed     327
routine_minimal    minimal    succeeded  118
race               race       succeeded    1
```

`marketplace_langgraph` / `marketplace_langchain` are hardcoded
`{"ok": False, "status_code": 501, "error": "adapter_unavailable"}`.

## Root cause class

**A capability catalog that advertises entries the executor cannot run.** The
preset catalog listed 8 architectures; 2 had no adapter. Nothing stopped a
routine pinning itself to one, so it failed on every run forever - and because
those runs never produced a win, the learning loop they fed stayed empty.

Three separate failures share the one class:

1. **False capability** - the same shape as a README claiming Wasm sandboxing
   with zero callers, or `just_works` reporting `ok: True` for an uninstalled
   Ollama. A name in a catalog is a promise; if the executor cannot honour it,
   the catalog is lying.
2. **Wrong instrument for a permanent fault** - the governor's error-streak
   pause distinguishes a *flaky* routine from a broken one. That question does
   not arise when the run is impossible, so waiting out the streak spent 327
   scheduler slots re-learning a fact knowable before the first run.
3. **A starved loop looks identical to a broken algorithm.** The instinct on
   seeing "OSR never returns known" is to blame the similarity function and
   reach for a better representation. The similarity function was fine. Nothing
   was ever *written*, and no embedding fixes an empty table.

## Invariant gap

- **Missing rule:** a capability registry entry must be derived from, or
  checked against, the executor that fulfils it. Availability must not be a
  hand-kept second list - implementing an adapter should flip the flag with no
  second edit.
- **Missing rule:** a permanent failure and a transient one need different
  controls. A retry budget applied to an impossible operation is a loop.
- **R-0011** covers the reporting half (degradation must be visible), but not
  the selection half - nothing stopped the *scheduler* choosing the thing that
  could only degrade.

## Notes

The strategic conclusion is the valuable part: **the decision layer did not
need a better model.** Once the stubs stop being selectable and permanent
failures are parked, `auto` routines race, the scoreboard fills, and `known`
becomes reachable with the deterministic feature hash that was already there -
verified by seeding a family and watching `classify` return
`band=known, winner=minimal`.

Separately, that feature hash was being called "the JEPA family gate" in three
modules while `action_value.py` correctly documented "There is no JEPA training
here". It is a SHA-256 bag-of-words hash: no learning, no prediction, purely
lexical. Renamed. Real representation learning stays an open architecture
decision rather than something the code silently claims to do already.

Measure before rewriting: `SELECT COUNT(*)` on the table the algorithm learns
from costs nothing and would have redirected this entire investigation in the
first minute.
